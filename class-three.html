1. Save the file in the right project

Project root means the practice-app folder containing package.json. Keep the root tsconfig.json there. Save the downloaded test inside its framework folder:

practice-app/
  package.json
  tsconfig.json                ← app TypeScript settings
  cypress.config.ts            ← Cypress runner settings
  cypress/
    tsconfig.json              ← Cypress editor/type settings
    e2e/
      class-three-student.cy.ts
  tests/
    playwright/
      class-three-student.spec.ts

The folders cypress/e2e and tests/playwright hold tests; they are not the folder from which to run npm commands. Do not move package.json or the root tsconfig.json into them.

Why are there two tsconfig.json files? What do red underlines mean?

tsconfig.json configures TypeScript’s editor and type checks. The root file describes the application source. The separate cypress/tsconfig.json tells the editor that Cypress specs use globals such as cy, Cypress, describe and it. It does not start Cypress; cypress.config.ts is the runner’s configuration.

The updated starter uses this Cypress-specific configuration:

{
  "extends": "../tsconfig.json",
  "compilerOptions": {
    "types": ["cypress"],
    "noEmit": true
  },
  "include": ["**/*.ts", "../cypress.config.ts"]
}

These browser specs need Cypress types. Adding node to types without installing its matching type package creates another editor error. Do not delete the app’s root configuration, overwrite your saved settings, or create more configuration files to hide errors. Older kits may lack the separate file; ask your instructor for the starter update.

After an instructor-approved configuration update, save your files and reopen the affected spec. If the underline remains, use VS Code’s command palette → TypeScript: Restart TS Server. Read the actual diagnostic: a type warning and a failed browser test are different problems. From practice-app, this command checks the Cypress TypeScript project:

npx tsc --project cypress/tsconfig.json --noEmit

Recall and explain

Does a successful click prove the requirement?

No. Assert the expected visible result or state.

Can the same new-tab strategy be copied between frameworks?

No. The Cypress example validates and follows the link in the same tab. Playwright separately verifies an actual popup.

Coverage and limits

This library covers common component interactions with small deterministic fixtures, including negative cases. It does not claim every framework API or every browser feature is covered. Cross-origin authentication, payment-provider frames, real email, CAPTCHA, performance and full accessibility audits require separate approved environments.

Drag events in Cypress and same-tab navigation are explicitly labeled approximations. Open shadow DOM is supported here; closed roots are a different boundary. Testing a responsive layout does not prove accessibility.
